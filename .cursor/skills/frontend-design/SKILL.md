# Frontend Design

## 适用场景

- 用户希望做页面/组件视觉改造。
- 用户需要把设计需求转成可交付前端代码。
- 用户要求统一设计风格、状态反馈、间距和排版。
- 用户明确提到响应式适配或可访问性改进。

## 默认工作流

按下面顺序执行，避免“只改样式不改体验”：

1. 明确目标：确认目标用户、核心任务、成功指标（可用性/转化/效率）。
2. 梳理信息层级：先确定页面主次，再决定视觉权重（标题、摘要、操作按钮）。
3. 设计结构：先布局（区块、网格、间距），再细化颜色、圆角、阴影。
4. 定义状态：补齐 loading/empty/error/disabled/hover/focus/active。
5. 实施与校验：实现后检查响应式、键盘可达、对比度与可读性。

## 设计与实现原则

### 1) 一致性优先

- 优先复用已有组件与 token（颜色、间距、字号、圆角、阴影）。
- 新增样式前先检查是否已存在等价模式。
- 相同语义使用相同视觉表达：主按钮、危险操作、提示信息保持一致。

### 2) 信息层级清晰

- 通过字号、字重、留白建立层次，不靠堆砌颜色。
- 每个区域只保留一个主操作，其余操作降级为次按钮或文本按钮。
- 长列表场景优先保证扫描效率（标题可读、关键元数据可快速比较）。

### 3) 交互状态完整

- 必须定义并实现：默认、悬浮、按下、聚焦、禁用。
- 异步行为必须可感知：按钮 pending、骨架屏或 loading、错误可恢复。
- 删除/危险操作提供二次确认或可撤销机制。

### 4) 响应式与可访问性

- 先保证 320px 起可用，再增强大屏布局。
- 交互元素可键盘操作，焦点样式清晰可见。
- 文本与背景保持足够对比度；图标不作为唯一信息来源。
- 表单错误要同时有颜色与文本说明。

## 与代码协作规则

- 改动前先读取相关组件，避免重写已存在能力。
- 样式修改优先小步迭代，保持行为不回归。
- 对复杂视觉决策提供简短理由，便于评审与后续维护。
- 涉及交互逻辑变化时，明确说明旧行为与新行为差异。
